# CSIG-2026 赛题二：评分逆向与技术结论

记录截至 2026-08-01 的全部实验数据与结论。**最重要的一条：评分公式已经解出，且经四点超定验证。**

---

## 一、评分公式（核心结论）

```
综合分 = 感知分 × 加速比^0.204
```

即 `Score = 33.183 · p · T^(-0.2039)`，其中 `p` 是相对 LQ 原图的感知分（`p_LQ ≡ 1`），`T` 是评测 harness 计到的推理墙钟毫秒数。

### 怎么解出来的

关键在于设计了**自标定的探测包**：`runner.py` 在 `__init__` 里量一次 GPU 吞吐、算出要跑多少次 matmul 才凑够目标墙钟时间。这样无论评测机是什么卡，`infer` 的耗时都精确等于设定值（实测误差 ≤1.6%）。于是能把「画质」和「时延」两个变量彻底解耦：

- **只改时延**：同一批图（逐字节相同）配不同定时 runner → 纯时延曲线
- **只改画质**：不同图配同一个恒等 runner → 纯感知分比值

### 拟合与验证

三个定时点做最小二乘，第四点（恒等 runner）独立校验：

| T (ms) | 实测 | 拟合 | 误差 |
|---:|---:|---:|---:|
| 5.0 | 23.9718 | 23.9007 | 0.3% |
| 20.0 | 17.9292 | 18.0161 | 0.5% |
| 182.0 | 11.5063 | 11.4849 | 0.2% |
| 恒等(≈0.023) | 71.5596 | — | 反推等效耗时 0.0231 ms，合理 |

指数由**四条独立途径**得到 0.2009 / 0.2039 / 0.2000 / 0.2039——就是 0.2。

曾用「乘性线性于加速比」`Score = P·(1 + 13.47/T)` 拟合同样的三点也是零误差（恰定），是 5 ms 那一点把它证伪的：线性形式预测 39.58，实测 23.97，幂律预测 23.69。**选 5 ms 是因为两个假设在该点相差 67%，而 20 ms 处只差 6.5%、182 ms 处完全重合。**

### 解出的量

| 量 | 值 |
|---|---|
| 指数 α | **0.2039** |
| 感知分（同一尺度） | 模型增强图 **88.10** / LQ 原图 **33.18** / USM3.5 **27.21** |
| 感知分比值 p | 模型 **2.6549** / LQ **1.0000** / USM3.5 **0.8199** |
| 提交 A 的等效耗时 | **30.5 ms**（评测 harness 计的那段） |

从当前 43.8908 出发：

| 动作 | 新分数 | 增益 |
|---|---:|---:|
| 速度 2× | 50.55 | +15.2% |
| 速度 4× | 58.23 | +32.7% |
| 速度 10× | 70.19 | +59.9% |

**感知分线性进入总分，速度是 0.2 次方。同等相对改进，画质的价值是速度的 5 倍。**

### 降内部分辨率的盈亏平衡线

若新方案快 x 倍、但只保留「相对 LQ 的画质增益」的 f 比例：

| 提速 | 需保留的画质增益 |
|---:|---:|
| 2× | > 78.9% |
| 4× | > 60.5% |
| 8× | > 44.6% |

内部降到 256×256 约为 4× 提速，**只要画质增益保住 60% 以上就净赚**。此判据可在本地验证，无需消耗提交额度。

## 四、指标选择：LPIPS 与 NIQE 都是错的

用三组已知 `p` 的图反查哪个 IQA 指标能复现实测排序（**模型 2.655 > LQ 1.000 > USM3.5 0.820**）：

| 类别 | 能排对序 | 排错序 |
|---|---|---|
| 有参考 | **TOPIQ-FR** | LPIPS、DISTS |
| 无参考 | **MANIQA** | MUSIQ、TOPIQ-NR、NIMA、NIQE、BRISQUE、HyperIQA |

除 TOPIQ-FR 与 MANIQA 外，**所有指标都把过锐化的 USM3.5 排在 LQ 原图之上**，与实测矛盾。PSNR/SSIM 更是完全反向（LQ 最高、模型最低，而模型的 `p` 是 LQ 的 2.65 倍）。

**后果：此前基于 LPIPS/NIQE 做的全部画质判断都不可靠**，包括 prompt 优化那一轮，需要用 TOPIQ-FR + MANIQA 重做。

拟合出的候选映射（两权重同号才物理合理）：

```
p ≈ 13.674 · TOPIQ-FR + 4.477 · MANIQA − 5.731
p ≈ 12.309 · (1 − LPIPS) + 3.870 · MANIQA + 4.851
```

⚠️ 3 方程 3 未知量（含截距），**必然精确解，零验证价值**。要确认需要第 4 组已知 `p` 的图。若验证通过，之后所有画质改进都能离线评估，不再消耗提交额度。

按当前拟合，有参考项的权重约为无参考项的 3 倍（两者量纲相近，均在 0~1 区间）——**优化方向应偏向「更接近 GT」而非「看起来更锐」**。

## 五、退化模型：这是一道伪装成 1× 的盲超分

> ### ⚠️ 2026-08-01 更正：本节原标题写的是「2× 超分」，**这是错的，退化强度约为 7×**
>
> 原判据「LQ 自往返 2× 得 46–51 dB」只证明 LQ **至少**被 2× 带限了 —— 那是下界，不是辨识。
> 一张被 7× 糊过的图，2× 往返当然也几乎无损。
>
> 用感知代理分（TOPIQ-FR + MANIQA，12 个验证集 crop，LQ 基线 `p_rel ≡ 1.000`）重新定位：
>
> | GT 重采样 | 2× | 4× | 6× | **≈7×** | 8× |
> |---|---:|---:|---:|---:|---:|
> | p_rel | **7.360** | 3.860 | 1.514 | **≈1.0** | 0.708 |
>
> | GT 高斯 | σ=2.0 | σ=3.0 | σ=3.5 | **σ≈3.6** | σ=4.0 |
> |---|---:|---:|---:|---:|---:|
> | p_rel | 3.412 | 1.682 | 1.131 | **≈1.0** | 0.750 |
>
> **后果：本节末尾原来那条训练配方（「2× area 下采样 + cubic 上采样」）会把 LQ 输入造得
> p_rel = 7.36 —— 已经逼近 GT 的天花板 8.336，模型会直接学成恒等映射。已作废，见下。**
>
> 注意：直接用 PSNR 对拍会得出 σ≈2.0，但整个退化族的 PSNR 只在 27.2–28.9 dB 之间摆动，
> 识别是病态的（PSNR 被低频主导，而低频恰恰是所有这些算子都保留的）。以感知匹配为准。

把图自己 2× 下采样再上采样，与原图比 PSNR：

| | LQ 自往返 | GT 自往返 |
|---|---:|---:|
| case1 | **50.44** | 37.29 |
| case2 | **46.48** | 34.85 |
| case3 | **50.93** | 39.26 |

**LQ 几乎能被自己的半分辨率版本无损重建（46–51 dB），GT 不能（35–39 dB）** → LQ 是带限的，截止在半 Nyquist，本质上就是某个源 2× 下采样再上采样的产物。

### 由此推出的两条硬结论

**1. 锐化/反卷积在数学上必输。** 最优线性滤波器在**每个频率**上的增益都 <1（DC 处 1.013，其余 ≤0.9）；`f > 0.19 cyc/px` 处 LQ 与 GT 的残差能量 ≥ GT 能量本身，即完全不相关——那段信息是被摧毁的，不是被可逆核卷积的。这解释了 USM3.5 为什么掉 12.88 分。留一交叉验证下，连最优滤波器本身都只有 −0.061 dB，不泛化。

**2. LQ 里没有噪声，去噪无用。** Immerkaer 估计：LQ 的 σ 为 0.19–0.37，GT 反而是 0.46–1.03；case3 的 LQ 平坦区 std 严格为 0。此前从频谱「极高频回升」推断有噪声是误读——那是重采样振铃，绝对能量仍比 GT 低 8 倍。实扫 323 组去噪参数，能通过「三图 PSNR/SSIM 同时不降」的只有 9 个，增益 +0.009~+0.018 dB。

### 唯一找到的正收益

全局对比度过冲：最优仿射 `gt ≈ a·lq + b` 的系数 a 在 **9/9 个（图×通道）组合上全部 <1**（0.890–0.976），说明 LQ 的对比度被系统性拉高。配合「黑位压死」门控信号（case3 的 LQ 有 5.82% 像素压死在 0，GT 是 0.000%），做轻微对比收缩可得 **+0.238 dB / +0.0157 SSIM**，两张干净图逐位不变。

`Moebius/tools/degrade.py`，字节级/感知级标定如下：

```
LQ = JPEG(clip(a ⊙ (k_aniso ⊛ GT) + b, 0, 255), quality=95, subsampling=4:2:0, 仅写 JFIF APP0)
```

而同流程反解**已知的**合成退化能到 47.6 dB —— 这 20 dB 的结构性落差说明 GT→LQ 里存在显著的
非 LTI 成分，任何单一 LTI 配方都配不平。

## 七、工程技术结论

### 7.1 fp16 下 tile 融合权重下溢（真 bug，原版 `hypir_infer.py` 同样存在）

`make_tiled_fn` 的高斯融合权重跨 11 个数量级（峰值 15.9，角落 2.3e-10）。fp16 最小次正规数是 6e-8，**2.2% 的权重直接下溢为 0**；而归一化用的 `count` 在 fp64 下算出、包含这些贡献——分子丢了分母没丢，tile 角落系统性偏暗。

端到端影响：**fp16 从 29.97 dB 提到 57.93 dB**（相对 fp32 基准）。修复是把融合权重与累加缓冲固定为 fp32，与模型 dtype 解耦。

修复后 fp16 优于 bf16（57.93 vs 43.55 dB），符合尾数位数预期（11 vs 8 位）。

### 7.2 Triton 的 `attn_d512` 在 Volta(sm70) 上算错

| N | custom_op vs fp32 参考 | **triton vs fp32 参考** |
|---|---:|---:|
| 64 | 8.7e-4 | **7.8e-1** |
| 4096 | 1.1e-4 | **1.3e-1** |

输出本身量级仅 0.03，误差 0.13–0.78 即结果无效。端到端 PSNR 从 42.55 掉到 27.32 dB。且它在 sm70 上还比直接走 SDPA **慢 16%**（1.940 vs 1.675 ms）——纯负收益。sm86 上无此问题。

已在 `triton-version` 分支加入自检：`Runner.__init__` 用 64×512 小输入实测一次（约 1 ms），不通过就把 attn 单独降级到 SDPA。实测 V100 上拦下、3080Ti 上放行。

### 7.3 ConvTranspose 折叠（数学精确，2.2–2.3× 加速）

`nearest 上采样 + 3×3 conv(pad=1)` 可精确折叠为 `ConvTranspose2d(k=4, s=2, p=1)`：

```
V[0]=W2,  V[1]=W1+W2,  V[2]=W0+W1,  V[3]=W0
```

float64 实测相对误差 **2e-16**（机器精度），边界也等价。乘加数从 `9·C·O·4HW` 降到 `16·C·O·HW`（4/9）。六处（VAE 解码器 3 + UNet 3）实测 19.97 → 8.98 ms。

⚠️ **验证时的陷阱**：GPU 上初测误差 2e-4，看着像折叠写错了——实为 cuDNN 对 fp32 卷积默认开 TF32（10 位尾数）。**等价性验证必须在 CPU float64 上做。**

### 7.4 custom_op_cpp_ext（CUDA C++ 替换 Triton）

V100(sm70) 逐算子相对 Triton 的加速比：

| 算子 | 加速比 |
|---|---|
| geglu | 1.02 – 5.04× |
| sample_latent | 3.15 – 3.63× |
| attn_d512 | 1.03 – 3.90×（且修正了正确性） |
| group_norm_act | 0.70 – 3.86× |

端到端 512×512：eager 182.42 / triton 89.37 / **custom 86.48 ms**。

`attn_d512` 刻意没写 flash：Volta 无 `cp.async`、无 `mma.16816`，flash 的 `BLOCK_M×512` fp32 累加器会把 occupancy 压死；N=4096 时物化分数矩阵仅 33.5 MB，两次 GEMM 交给 cuBLAS 更划算——实测印证。

`group_norm_act` 初版比 Triton 慢 50 倍，原因是 stats kernel 只按 `cpg` 分线程，`cpg=4`(C=128) 时 256 线程只有 4 个在干活。改成按 (行, 组内通道) 二维铺开后修复。

### 7.5.1 算子后端与内存布局是绑定的

四个融合算子（`group_norm_act` / `geglu` / `sample_latent` / `attn_d512`）现在集中在 `model_dir/csig_ops.py`，三种实现由 `CSIG_OP_BACKEND` 选择：

| 后端 | 实现 | 布局 | V100 `infer(512)` |
|---|---|---|---:|
| `pytorch` | eager | NCHW | 149.51 ms |
| `triton` | 本文件内的 Triton kernel（运行时 JIT） | NHWC | 96.81 ms |
| `cuda` | `custom_op_cpp_ext` 的 CUDA C++ 扩展（需预编译 `.so`） | NHWC | **86.70 ms** |
| `auto`（默认） | 可用后端各实测一次取最快 | 随后端 | 87.42 ms |

**布局不能独立于后端选**：triton/cuda 的 kernel 都按 NHWC 寻址，是硬要求；而纯 PyTorch 下 NCHW 更快。所以 `channels_last` 跟着后端走（`config.yaml` 里显式写 true/false 才覆盖）。

`triton` 的 `attn_d512` 在 sm70 上算错，`bind()` 里用 64×512 小输入实测一次自检，不过就单独把 attn 降级到 SDPA——V100 上实测拦下。

三后端输出互差 50~53 dB，与这条管线自身的跨进程噪声底（53.8 dB）同量级。

纯 PyTorch 下两台卡都是 NCHW 更快：

| GPU | NHWC | NCHW | 提速 |
|---|---:|---:|---:|
| Tesla V100 (sm70) | 182.70 | **150.10** | 1.22× |
| RTX 3080Ti Laptop (sm86) | 224.52 | **192.50** | 1.17× |

V100 分段（新 `infer`，512×512）：

| 段 | NHWC | NCHW | |
|---|---:|---:|---|
| VAE encode+sample | 52.30 | **33.06** | −37% |
| UNet+ddpm | 36.99 | 38.26 | +3% |
| VAE decode | 102.36 | **82.94** | −19% |
| wavelet | 1.22 | 1.26 | |

差距全在 VAE，UNet 反而略输——若日后要极致优化，可考虑 VAE 走 NCHW、UNet 走 NHWC 的混合布局（估算约再省 1 ms，收益很小）。

**注意 VAE 占 78%（116/149 ms），UNet 只占 25%。** 融合 GroupNorm+SiLU（Triton/custom_op）攻的正是 VAE，这解释了它凭什么把 182 ms 打到 90 ms。

由于评测机型号未知（见第八节，它比这台 V100 快约 3 倍），默认走 `CSIG_OP_BACKEND=auto`：`Runner.__init__` 把可用后端各实测一次 512×512 热路径取胜者，代价约 6 s 加载时间（V100 上 auto 正确选中 cuda）。

### 7.5.2 `infer` 与 `enhance` 拆分

赛题只在 512×512 上量 `infer` 的时延，故 `infer` 收窄为一条形状恒定、无 RNG、无 prompt 依赖的单 tile 路径；整图所需的短边保护、pad、三段 tiled 融合移到 `enhance`（`main.py` 用）。

拆分本身在 V100 上只值 **0.15 ms**（182.70 → 182.52）——旧 `infer` 在 512×512 下本来就走单 tile 快路径。真正的价值是**消除 prompt 风险**：旧实现一旦收到与 `config.yaml` 不同的 prompt 就要付 tokenizer + 23 层 CLIP 前向（3080Ti 实测 3.736 ms，V100 约 6 ms）+ 16 组 K/V 投影；逐图变化则每次都付。现在条件 embedding 在 `__init__` 编码好常驻，`prompt` 形参完全不参与计算。

等价性：同进程内用旧函数体 + 新实例（共享权重与 cuDNN 状态）比对，`infer(512)` / 9-tile / 49-tile / 4096×3072 整图四条路径全部 `torch.equal=True`。

### 7.5.3 这条管线跨进程不可复现

同一份代码、同一台机器、两个进程，512×512 输出的 PSNR 只有 **53.8 dB**（maxdiff 0.25），关掉 `cudnn.benchmark` 也一样。**`output_dir/` 无法逐位重跑**，所有等价性验证必须在同一进程内做。

### 7.5.4 nsys kernel 分布与几条被证伪的优化假设

V100、cuda 后端、512×512，GPU 忙时 84.79 ms/iter，**1097 次 kernel launch**：

| 项 | ms/iter | 占比 |
|---|---:|---:|
| 卷积 fprop（cuDNN NHWC implicit GEMM） | ~40 | ~47% |
| `CUDAFunctor_add` × 265 | 9.55 | 11.3% |
| `gn_stats`×113 + `gn_apply`×95 + finalize | 10.4 | 12.3% |
| mem-efficient attention × 32 | 6.0 | 7.1% |
| ConvTranspose `dgrad_implicit_gemm_indexed` × 6 | 4.98 | 5.9% |
| cast / copy / fill / mul | ~2.0 | 2.4% |

**ConvTranspose 换成子像素卷积 —— 假设被证伪。** `dgrad_implicit_gemm_indexed` 看着像慢路径（stride>1 的索引式 gather），但实测它就是最优的。四种数学等价实现（float64 验到 5e-15）在 V100 的 6 个生产形状上：

| 实现 | NHWC 合计 ms | 相对 |
|---|---:|---:|
| **ConvTranspose(k4,s2,p1)（现状）** | **6.103** | **1.00×** |
| 子像素 k=2 + 子格写回（MAC 相同） | 6.633 | 0.92× |
| nearest + conv3x3（折叠前） | 11.171 | 0.55× |
| 子像素 k=3 + pixel_shuffle（MAC 2.25×） | 13.125 | 0.46× |

只有最小的 `1280ch 8→16` 那一档 nearest 略快（0.165 vs 0.186 ms），不值得为此加分支。**结论：不动。** 复现见 `csig_bench/upsample_bench.py`。

**conv+add 用 cuDNN 融合 —— 不做。** sm70 的 legacy `cudnnConvolutionBiasActivationForward` 支持 `conv+bias+alpha2·z`，但 PyTorch eager 不暴露，且 `ACTIVATION_IDENTITY` 会把算法锁到 `IMPLICIT_PRECOMP_GEMM`；现在 cuDNN 给我们挑的是 `tilesize128x128x32` 的 tensor-core kernel，换算法大概率亏更多。

**265 个 add 里能融的只有一部分。** 按 trace 里「add 的下一个 kernel 是谁」分类：

| add 之后 | 个数/iter | ms/iter |
|---|---:|---:|
| `gn_stats` | 101 | 5.34 |
| 其他 | 82 | — |
| 又一个 add | 68 | — |
| conv | 16 | — |

可融的 101 个里，耗时又高度集中：12 个 ≥200 µs 的占 3.13 ms（全在 VAE 高分辨率段），47 个 <10 µs 的（UNet latent）只占 0.244 ms。

**CUDA Graph 的 RNG prologue —— 确认存在但不值钱。** `CUDAGraph.replay()` 无条件填 philox seed/offset（我们的 `_infer_tile` 零 RNG），trace 里是开头两个 `vectorized_elementwise`。但只有**第一次** replay 后面有 147 µs 空隙，第二三次只有 1.3 µs，摊下来约 5 µs/iter = **0.006%**。CTI-2026 的 `_SkipPrologueFill(TorchDispatchMode)` 修复在那边值 0.5%（模型只跑 ~1 ms），在这里不值得单独做。

### 7.5.6 GroupNorm 统计量 kernel：占用率 1.33x + 访存合并 1.25x，但净收益为 0

nsys 里 `gn_stats` 3.40 ms/iter，最大 20 次占 73%。诊断脚本 `csig_bench/gn_bandwidth.py` 量出来它在 V100 上远离 roofline，而同形状的纯 `add` 处处贴着 roofline：

| HW × C | cpg | add 效率 | **stats 效率** | apply 效率 |
|---|---:|---:|---:|---:|
| 262144×128 | 4 | 1.00 | **0.35** | 0.77 |
| 65536×128 | 4 | 0.99 | **0.32** | 0.86 |
| 262144×256 | 8 | 1.01 | **0.73** | 0.99 |
| 65536×512 | 16 | 1.00 | 0.86 | 0.97 |

原因是 `_gn_stats_kernel` 按 `(n, g)` 分组遍历，NHWC 下每行只读 `cpg` 个 half：cpg=4(C=128) 时只有 8 字节落进 32B sector。**注意这是 sm70 特有的**——同一个 kernel 在 sm86 上效率有 0.91。

**但收益拆开来看，主因不是访存合并：**

| V100，五个 cpg<16 形状合计 | ms | 相对 |
|---|---:|---:|
| 旧 kernel，`_gn_config` 的 split（≤16） | 0.683 | 1.00× |
| 旧 kernel，split=64/128 | **0.511** | **1.33×** |
| 新的按行连续 kernel（`_gn_stats_nhwc_kernel`） | **0.410** | **1.66×** |

**1.33× 来自占用率**（split 上限 16 把大形状压在 512 个块上），只有余下的 1.25× 才是访存合并。这也解释了 CUDA 版为什么改了没反应：`group_norm_act.cu` 的 `pick_split` 本来就开到 64，占用率够了，L2 把那些 8 字节碎片吸收掉了——照搬同一个「合并访存」kernel 到 CUDA 侧实测**零收益**，已回退。

两项都落地在 Triton 侧后（split 启发式改为按 `group_elems/8192` 缩放、上限 128；cpg<16 且 C 为 2 的幂时走新 kernel），同进程 A/B：

| | `_infer_tile` (V100) |
|---|---:|
| 改动前 | 85.79 ms |
| + split 启发式 | 84.83 ms |
| + 按行连续 kernel | **84.10 ms** |

**净收益为 0。** 因为 cuda 后端本来就在 84.75 ms，这轮只是让 triton 后端**追平**它——同进程交替测完整 `infer`，triton 87.29 / cuda 87.32，实质相同。机器上最好的那条路径没有变快。

保留它的理由是保险：评测机若加载不了预编译的 `.so`，`auto` 会退到 triton，而 triton 现在比之前快 2%。

⚠️ **跨进程测后端快慢会得到错误结论**：同一份 triton 代码在独立进程里测出 90.7~96.8 ms 的散布（JIT 状态 + cudnn autotune 各跑各的），而 cuda 是 86.7~87.8。必须同进程交替测。这也是 `auto` 选型把 `_warmup` 的计时次数从 3 提到 10 的原因——3 次的噪声足以让 0.8% 的差距变成抛硬币。

### 7.5.8 更小的分块：速度 +9%，但画质代价大且与「无接缝」互斥

注意力是 O(N^2)（N = latent token 数），512x512 -> N=4096；切成 4 块 256x256 后每块 N=1024，注意力总量降到 1/4，而卷积是线性的、总量不变。V100 实测（`csig_bench/tile_size_bench.py`）：

| 配置 | latent N | 注意力相对量 | ms | 相对 512 |
|---|---:|---:|---:|---:|
| (1,3,512,512) 现状 | 4096 | 1.000 | 84.15 | 1.00x |
| **(4,3,256,256) 打包** | 1024 | 0.250 | **77.06** | **1.09x** |
| (16,3,128,128) | 256 | 0.062 | 77.44 | 1.09x |
| (64,3,64,64) | 64 | 0.016 | 85.68 | 0.98x |
| 4x(1,3,256,256) 串行 | 1024 | 0.250 | 239.02 | 0.35x |

收益到 256 就停（128 持平、64 反而更慢——kernel 掉进 0.045 ms 的启动地板，且注意力已不是瓶颈）。**必须按 batch 维打包**：串行慢 2.8 倍，多付的 launch 远超省下的注意力。

**代价**：与 512 单块相比 PSNR **27.98 dB**（管线自身的跨进程噪声底是 53.8 dB，所以这是实质不同的输出）；接缝处相邻列差 0.0456 vs 全图典型 0.0172，即 **2.65x**（512 单块在同一位置是 0.52x，无不连续）。

接缝可用重叠+高斯融合消掉，但 512 内部用 stride=128 就是 3x3=9 块、2.25 倍工作量，比基线还慢——**「9% 提速」与「无接缝」互斥**。

另外还有合规问题：评测计 `infer` 的时延是作为「产出提交图片的代价」的代理。若 `infer` 内部用比 `enhance` 更便宜的分块，量到的时延就对不上提交的画质。要正当地拿这 9%，得用同样的分块重跑 `output_dir` 并再烧一次提交额度重新标定 `p`——而 `p` 线性进分，28 dB 的画质变化很可能亏得比 1.8% 多。

**顺带抓到的 bug**：`triton_attn_d512` 的 grid 是 `(N/BLOCK_M,)`、寻址里没有 batch 维，batch>1 时只算第 0 个、其余留在 `torch.empty` 的未初始化内存里——静默出错。已在 `_guard_attn` 加 `q.shape[0] == 1`，batch>1 回退 SDPA。CUDA 版本来就 `TORCH_CHECK` 报错，现在两边对齐。

### 7.5.7 残差 add 融进 group_norm_act：不做

可融合链路（add 紧跟 `gn_stats`）101 处/iter、15.5 ms（占 GPU 时间 18.3%），理论上省 6 遍访存里的 1 遍。写了真的融合 kernel 实测：3080Ti 上 per-shape 调优后合计 **+5.3%**（C=128 那两组因 `cpg=4` 时融合版的 store 只有 8 字节连续而亏 16~24%），V100 上用非融合版的调优表跑是 **−47.5%**。

折算端到端 0.95%~2.32%，即 +0.19%~+0.48% 分，而代价是把 `(主干, 待加残差)` 元组穿过 `ResnetBlock2D` + 8 个容器类——**在提交文件里做结构性改动**。低于事先定的 ≥2 ms 门槛，不做。复现见 `csig_bench/fusion_bench.py`。

### 7.5.5 temb 折进 conv1.bias

UNet 的 22 个 resnet 都有 `h + time_emb_proj(silu(temb))`，而 timesteps 恒定 ⇒ 该项是逐通道常量 `(1,C,1,1)`，**语义就是 bias**。加载期折进 `conv1.bias` 后，整条 timestep 通路（`_cached_temb`、`temb` 参数、`timesteps` 参数）都能从前向删掉。

精确性：与折叠前对比 PSNR **71.6 dB**（差异只是 fp16 下 bias 相加与激活相加的舍入次序）。但**端到端提速量不出来**——那 22 个 add 在 latent 分辨率，合计不到 0.1 ms，落在 V100 的运行间波动（±1.4%）以内。保留它的理由是代码更简单、少 22 次 launch，不是速度。

### 7.6 Python 3.9 兼容性（曾导致提交失败）

评测机是 Python 3.9.25，PEP 604 的 `X | Y` 类型注解会在**函数定义时**报错。这是 `Bad input file` 的成因。已改为 `Union[X, Y]` / `Optional[X]`。

`Bad input file` 出自阿里天池评测脚本模板：`error_msg = {1: "Bad input file", 2: "Wrong input file format"}`，是 `except Exception` 的兜底文案，等价于「评测脚本抛异常了」，与压缩包是否损坏无关。

### 7.7 打包的 ZIP64 陷阱

Python `zipfile` 的 ZIP64 阈值是 **2 GiB**（`ZIP64_LIMIT = 2**31-1`）而非 4 GiB。3.04 GB 的包会让 4 个 `model_dir` 条目写成 `extract_version=45` + ZIP64 extra。`busybox unzip` 本地已复现 `bad archive`。改用 Info-ZIP `zip -0 -X -D -r` 可完全消除。

（注：实际提交能出分，说明天池平台的解压器支持 ZIP64，此项非阻塞。）

## 八、「3 倍疑点」已结案：评测机比我们的 V100 快约 3 倍，但不影响优化方向

提交 A（Triton）反推 30.5 ms，同一份代码在 V100 实测 90.04 ms，差 2.95 倍——曾怀疑 harness 只计更窄的一段。

**排除依据是比值：**

| | Triton | 纯 PyTorch | 比值 |
|---|---:|---:|---:|
| 反推自得分 | 30.5 ms | 61.6 ms | **2.02** |
| V100 实测 | 90.04 ms | 182.04 ms | **2.02** |

三位有效数字一致。若 harness 只计其中一段，那一段必须在两个版本里都恰好占 1/2.95，而包装层只占 1.4%（tiled 包装 0.004 + wavelet 1.22 + 杂项）——不可能。故计时窗口就是完整 `infer`，差异来自机器。

**这不影响优化方向**：分数吃的是 `(T_OSEDiff / T)^0.2`，OSEDiff 基准跑在同一台机器上，机器速度在比值里约掉。V100 实测 175.31/90.04 = 1.95×，反推 59.4/30.5 = 1.95×，完全一致。**因此 V100 上量到的相对加速可 1:1 折算进分数**，这也是把实验放在 V100 做的依据。

唯一的副作用：评测机大概率不是 sm70，所以逐架构的旋钮（内存布局、kernel 选择）不能按 V100 结果硬编码，要么在加载期自选（已对 `channels_last` 这么做），要么选各架构都安全的值（SDPA 优先级 `[FLASH, EFFICIENT]` 属此类：V100 上 FLASH 不可用会自动落到 EFFICIENT，与显式指定 EFFICIENT 同速）。

## 九点五、任务本质判定与画质天花板（2026-08-01 新增）

### 9.5.1 任务是什么：伪装成 1× 的**盲超分**，唯一实质成分是强低通

| 候选 | 裁决 | 依据 |
|---|---|---|
| **超分（分辨率不变）** | ✅ **就是它** | −6 dB 截止在 0.046–0.100 cyc/px（Nyquist 0.5），等效 σ=1.85–4.06 |
| 图像恢复 | ✅ 上位类，对但不够具体 | — |
| 去模糊 | ⚠️ 形似而非 | 最优线性复原核在**每个**频段增益 ≤1，不存在可反卷积的 PSF |
| **去噪** | ❌ 明确否定 | LQ 平坦区 σ=0.014–0.090 灰阶（<1/10 LSB）；GT 反而更"脏"（0.17–0.30） |
| 增强（色调/对比） | ⚠️ 只占 1–3%（case3 22%），留一验证下**净负 −0.067 dB** | — |
| 修复 inpainting / 编辑 | ❌ | 无 mask、无空洞；几何严格对齐（旋转 <1.4e-4 rad） |
| JPEG 去伪影 / 色度上采样 | ❌ 可忽略 | 分别只占 0.2–1.6% / 0.06–0.15% 的 MSE |

**损失构成**：高频被摧毁 **78–98%**｜色调仿射 0.9–22%｜JPEG ~1%｜色度 ~0.1%｜噪声 **0**。

**最有行动价值的一个数**：残差能量的频率分布是 `f<0.15` 占 **86% / 41% / 89%**。
要复原的**不是 Nyquist 附近的微纹理，而是周期 7–33 px 的中尺度结构**（窗框、栏杆、枝叶、招牌笔画）。
「加高频锐化」方向就是错的，这也再次解释了 USM3.5 为什么掉 12.88 分。

另有一条会直接影响训练：**逐图残留 0.2–0.8 px 亚像素错位**（三种独立方法一致，符号逐图不同）。
这是 L1/L2 会把输出拉平的直接机制，训练必须以感知/对抗损失为主。

### 9.5.2 画质天花板：VAE 不是瓶颈，头顶还有 68%

12 个验证 crop，「保留增益」= `(p − p_LQ)/(p_GT − p_LQ)`：

| 配置 | TOPIQ-FR | p_rel | 保留增益 |
|---|---:|---:|---:|
| LQ（基线） | 0.4142 | 1.000 | 0% |
| **GT（绝对天花板）** | 0.9198 | **8.336** | 100% |
| GT 只过 SDXL VAE @512 | 0.9094 | 8.194 | **98.1%** |
| GT 只降采样 512→256→512 | 0.8369 | 7.060 | 82.6% |
| GT 降采样 + VAE @256 | 0.7350 | 5.668 | 63.6% |

- **VAE @512 只吃掉 1.9% 的可得增益** → latent 扩散路线成立，瓶颈在 UNet 生成能力。
- **现有 HYPIR 基线 p=2.65，只吃到 22.5% 的可得增益。头顶 77% 没拿。**
- **「VAE 内部降到 256」判负**：3.91× 提速但只保留 63.6% 增益，
  `Score 比 = (2.05/2.65) × 3.91^0.204 = 1.014`，净 **+1.4%**，在噪声里。

### 9.5.3 LQ 的可压缩性（决定能否套用 4× 超分模型）

| 把 LQ 压到 | vs LQ 的 PSNR | p_rel |
|---|---:|---:|
| 2×（256 px） | **50.14 dB** | 0.956（只掉 4.4%） |
| 4×（128 px） | 41.29 dB | 0.737（掉 26%） |

（对照：GT 压 2× 只有 38.69 dB）→ **编码端可以在 256 上做，压到 128 去套 4× 模型要付实质代价。**

### 9.5.4 测试集里有 9 张根本没被退化

`case 1, 2, 3, 4, 5, 38, 64, 65, 66` 是**相机原生 JPEG**，没进过主办方的退化管线。四路独立证据：

| 证据 | 数值 |
|---|---|
| 量化表指纹 | 91 张的量化表 md5 与 3 张验证集 LQ **完全相同**且只剩 JFIF；这 9 张是华为自研 ISP 表 + 完整 EXIF/MakerNote/MPF/ICC/增益图 |
| 双压检测 | 原生 8/8 命中（P=0.17–0.26）；91 张 + 验证集 LQ 全部 **0/8**（P≈0.002） |
| 尺度自相似（A−B） | 原生中位 **4.05**（GT 档）vs 重编码中位 **8.89**（LQ 档） |
| 同场景受控组 | 原生 7 张 HFR 0.0368 vs 重编码 5 张 0.00143 = **25.7×** |

### 9.5.5 验证集的代表性风险

验证集只有 3 张，全是**建筑/远景城市**。而测试集 100 张里 **26 张植被/花卉、6 张招牌文字、
5 张器物、4 张街景 —— 验证集覆盖为零**。所有离线评估都建立在这 3 张上，存在系统性偏差。

## 十、下一步建议

0. **【最高优先】按 9.5 节重做训练数据与主模型后训练**。旧的 2× 配方会把模型训成恒等映射。
1. **验证本地代理**（1 次提交）：提交 `LQ + USM1.0 + 恒等 runner`，与 TOPIQ-FR/MANIQA 拟合式的预测比对。通过则之后所有画质改进可离线评估，不再消耗额度。
2. **重做画质优化**：用 TOPIQ-FR + MANIQA 替代 LPIPS/NIQE 重新评估 prompt、模型选择等。感知分线性进入总分，是最大杠杆。
3. **速度：`cuda` 后端要解决 `.so` 的可移植性**。V100 上它是最快的（86.70 ms），但提交包必须带预编译的 `_C*.so`，要匹配评测机的 Python / torch / CUDA / 架构。`auto` 已经做到加载不了就自动退到 triton（96.81 ms），所以带上是纯赚——最坏情况等于不带。
4. **速度：CUDA Graph 的价值有限但非零**。V100 分段显示各段 CPU 下发之和约 52 ms、GPU 约 192 ms，整体 GPU-bound；但 UNet 那段 CPU 下发 36.99 / e2e 38.26，几乎纯 launch-bound，单独捕获 UNet 估计能省 10~20 ms（约 7~13%）。注意整条 `infer` 的下发时间总是接近 e2e，那是发射队列填满后的反压，不是 launch-bound 的证据。
5. **速度作为次要方向**：4× 提速值 +32.7%，但需保住 60% 以上的画质增益才净赚。

### 逐架构旋钮必须在评测机同型号上量

本地只能验精度。会改分的旋钮（内存布局、SDPA 后端、kernel 选择）在 sm86 和 sm70 上结论可以相反，且评测机型号未知——要么加载期自选（`channels_last` 已如此），要么选各架构都安全的值。
